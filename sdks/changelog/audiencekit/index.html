Changelog

One changelog for the whole SDK from 0.24.0 on. Earlier releases are in swift/CHANGELOG.md (through 0.23.0) and android/CHANGELOG.md (through 0.19.0).

0.86.0 (2026-11-21)

Section titled “0.86.0 (2026-11-21)”
  • Sliding-scale cover (Swift, Kotlin and Node; Rick, 2026-11-21, “build out sliding scale cover, max, min, suggested”). Needs audience_kit_api’s CoverCharge.scale and buyCover(amount:).
    • CoverCharge.scale (CoverScale: min, max, suggested), null for a fixed cover; the charge’s amount is then the suggested amount.
    • buyCover(venueID:amountCents:) / buyCover(venueId, amountCents): what the buyer chose for each cover, from min to max; left out, the suggested (or fixed) amount.
    • CoverScale.step / clamped (clamp in Kotlin): a picker’s whole-dollar steps, kept in the range.

0.85.0 (2026-11-21)

Section titled “0.85.0 (2026-11-21)”
  • cachedVenues(maxAge:) / cachedVenues(maxAgeMillis) (Swift and Kotlin; Rick, 2026-11-21, “venues list is slow to load”): the venues venues() last fetched, read from the GraphQL cache without asking the API, so a Venues screen draws at once and refreshes behind them. venues() now keeps its answer under a fixed cache key (venuesCacheKey / VENUES_CACHE_KEY, “Venues”) whatever the audience’s modules, so the list is found after a relaunch, before the session has learned the audience’s schema shape. Lists kept under the old key are fetched again once.

0.84.0 (2026-11-20)

Section titled “0.84.0 (2026-11-20)”
  • Sing-along nights (Swift and Kotlin; Rick, 2026-11-20, “showing the rotation / requesting a song flows” for Hot Mess 2.9). Reads what audience_kit_api already serves on production (#760, Venue.music.nowPlaying); nothing new is needed there.
    • singAlong(eventID:): whether an event is a sing-along (Event.karaoke.singAlong), its playlist (url, uri, shuffle, tracks) and its venue’s rotation now. nowPlaying(venueID:) refreshes the rotation alone. Both drop a report past its expiresAt.
    • NowPlaying (title, artist, artwork, upNext), SingAlongPlaylist, SingAlongTrack.
    • For the request picker: pickableTracks(matching:) (A to Z, searched by title and artist ignoring case, accents and punctuation) and status(of:): playing now, up next, requested by me, or in the queue. Requests go through the existing requestSong.
    • graphql/schema.graphql refreshed from audience_kit_api next.

0.73.0 (2026-11-16)

Section titled “0.73.0 (2026-11-16)”
  • On-device GraphQL cache (Swift and Kotlin; Rick, 2026-11-15, “build our local cache for data so we get less errors if data is flakey with a background update job”). Off unless the app passes one, so nothing changes for other callers.
    • AudienceSession(cache:defaultCachePolicy:): a GraphQLCache (FileGraphQLCache in Caches, readable after first unlock so background refreshes work; InMemoryGraphQLCache for tests) and the policy for calls that don’t pass one.
    • GraphQLCachePolicy: .networkOnly (default), .networkFirst(maxAge:) (the last good answer, a week at most, when the API can’t answer: offline, 5xx, GraphQL errors, undecodable responses; refusals such as 401/403/404 and undefinedField, which the SDK retries with fewer fields, still throw), .cacheFirst(freshFor:maxAge:), and .refresh (keep a good answer, never serve one: for background jobs that need to see failures and back off).
    • graphQL(...) takes cachePolicy: and cacheKey:; graphQLResult(...) says whether the answer is from the network or the cache, when it was fetched and why the API failed; cachedGraphQL(...) reads the cache only, for screens that show the last answer at once. Only queries are kept, plus mutations given a cacheKey. Entries are keyed by API, audience, person, endpoint and document plus sorted variables; sign-out and account deletion empty the cache, and entries past the default policy’s max age are pruned at launch.
    • layout(screen:...) keeps each screen’s layout under one key (Layout:<screen>), so a failing Layout request returns the last layout instead of failing (and an app that refetches on failure stops looping).
    • VisitedLocales: the locales the person has been in lately, on the phone only (UserDefaults, per audience, 5 within 30 days by default), for apps to choose what a background refresh keeps fresh.
    • RefreshBackoff: spaces background refreshes, doubling after each failure (15 minutes to 6 hours by default).
    • Kotlin: the same on AudienceKitClient(cache = …, defaultCachePolicy = …): GraphQLCachePolicy.NetworkOnly, NetworkFirst, CacheFirst, Refresh; graphQLResult, cachedGraphQL; FileGraphQLCache(directory) (pass a folder under context.cacheDir); VisitedLocales(store) with FileVisitedLocaleStore (under noBackupFilesDir); RefreshBackoff. Entries are keyed by the session token’s JWT sub. audiencekit-android: AudienceKitClient(context, …, cache, defaultCachePolicy), graphQLCache(context) and visitedLocales(context, audienceId).

0.25.0 (2026-10-20)

Section titled “0.25.0 (2026-10-20)”

GraphQL operations can be followed in an app’s monitoring (New Relic, say), by name, over HTTP and over the cable.

  • Every GraphQL request carries X-APOLLO-OPERATION-TYPE (query, mutation, subscription) and X-APOLLO-OPERATION-NAME (the operationName passed, else the name in the document). New Relic’s mobile agents record both with each network request, so HTTP operations show up by name with no app changes.

The agents can’t see inside the socket, so this is the only record of those operations.
  • GraphQLOperationEvent.describe(query:operationName:) reads an operation’s type and name from its document.
  • Swift APIRequest and Kotlin APIRequest take extra headers.
